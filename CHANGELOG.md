# Changelog

All notable changes to PptMcp (PowerPoint MCP Server) will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed

- **Session teardown no longer terminates a PowerPoint instance the user already had open** (#160): PowerPoint is a single-instance application, so `Activator.CreateInstance` attaches to the user's running `POWERPNT.EXE` instead of starting a second one. Teardown then called `Process.Kill()` on it — no save prompt, no recovery entry, and every unsaved deck the user had open lost. `SessionManager` documents the underlying behaviour itself ("Quitting one kills all"), but no ownership check existed at any of the three kill sites.
  - `PptBatch` now snapshots the running `POWERPNT.EXE` process IDs **before** creating the Application object, which identifies a process it started itself. For a process it merely attached to, it counts the presentations still open after closing its own during STA cleanup. Termination is withheld only when the user genuinely still has something open.
  - That second signal matters. Withholding termination on the attach signal alone stranded an instance that every later session then inherited — each declining to clean it up — while it held presentation files locked, which broke unrelated tests. It also makes the decision self-correcting when a previous session's PowerPoint is still shutting down as the next one starts, a race the start-time snapshot cannot see.
  - All three termination sites are gated: the pre-emptive kill on operation timeout, the force-kill after an STA join timeout, and the designed termination path at the end of disposal.
  - The multi-presentation path also called `Application.Quit()` unguarded. With `DisplayAlerts = ppAlertsNone` set on the shared Application object, that closed the user's decks without a prompt too. The single-presentation path had already avoided `Quit()` for exactly this reason; the two paths now agree.
  - The previous code carried a comment asserting that the two cases could not be distinguished and that skipping termination would leak a process holding files locked indefinitely. The first claim is false. The second was right about the failure mode but wrong about the remedy: STA cleanup closes every presentation the session opened *before* termination is attempted, and closing a presentation is what releases its file lock. Termination makes a process we started exit; it is not what unlocks files.
  - `ProcessOwnershipTests` asserts all three directions, so the fix cannot silently disable the #148 teardown win nor re-introduce the stranded-instance cascade: a process started by the session is terminated, an attached one still holding the user's deck survives, and an attached one with nothing open is terminated. Each attach case also asserts that single-instance attachment actually occurred, so it cannot pass vacuously.

- **The command layer no longer abandons COM proxies anywhere: the inline-chain ratchet reaches zero** (#137, #126): a second sweep took the remaining 63 chains across 20 files to **0**. Together with the previous sweep the repository ratchet has gone **173 to 0**.
  - The worst remaining offender was speaker notes. `slide.NotesPage.Shapes.Placeholders.Item(2).TextFrame.TextRange.Text` abandons five COM proxies in a single expression, and it appeared five times across read, set, append and read-all. It is now `ComUtilities.GetNotesText` / `SetNotesText`.
  - `BackgroundCommands` re-walked `slide.Background.Fill` for every operation, abandoning two proxies per statement and up to six in `SetGradient` alone.
  - `ImageCommands`, `MediaCommands`, `PlaceholderCommands` and `CommentCommands` abandoned the `Shapes`/`Comments` collection *and* discarded the newly created shape proxy returned by `AddPicture`, `AddMediaObject2` and `Comments.Add2`.
  - Adds fifteen further `ComUtilities` accessors: `GetShapeText`, `SetShapeText`, `GetPlaceholders`, `GetPlaceholderAt`, `GetNotesText`, `SetNotesText`, `GetSlideCount`, `GetShapeCount`, `GetBackgroundFill`, `SetForeColorRgb`, `SetBackColorRgb`, `GetSlideShowTransition`, `GetNamedSlideShows`, `GetCustomLayoutCount`, `GetSlideDesignName` and `GetPlaceholderTypeInt`.
  - Tracked COM acquisitions rise from 253 to **267**, and the undocumented `((dynamic))` cast baseline falls from 70 to **29** as a side effect of routing access through named helpers.

- **Four command files no longer abandon a COM proxy on every slide, shape, table-cell and colour access** (#137, #126): `ShapeCommands` (52), `TextCommands` (26), `SlideTableCommands` (19) and `ChartCommands` (13) all reached COM objects through inline chains such as `slide.Shapes.Item(name)`, `cell.Shape.TextFrame.TextRange.Text` or `fill.ForeColor.RGB`. Each hop materialises an RCW that is never bound to a local, so `ComUtilities.Release` could not be called on it **even in principle** — the try/finally pattern Rule 22 mandates cannot express a release for an object you never named.
  - This is not only hygiene. #148 established by measurement that a single leaked collection proxy is enough to stop the STA thread exiting, turning session teardown into a 45-second timeout (leaky 45093ms vs clean 5501ms).
  - Adds ten accessors to `ComUtilities` — `GetSlide`, `GetShape`, `GetShapeAt`, `GetTextRange`, `GetTextFont`, `GetCellText`, `SetCellText`, `GetTableRow`, `GetTableColumn`, `GetTableRowCount`, `GetTableColumnCount`, `GetForeColorRgb` — each binding the intermediate and releasing it in a `finally`.
  - Three cases leaked more than the chain count suggested: table cell access abandoned three proxies **per cell** inside a nested loop, so the leak scaled with the area of the table; `SetFill`/`SetLine`/`SetGradientFill` abandoned four `Fill` proxies plus a colour proxy per call; and `TextCommands.Format` released `font` and `textFrame` only on the success path, leaking both on any throw.
  - The repository ratchet drops from **173 inline chains to 63**, and tracked COM acquisitions rise from 221 to 253 — an acquisition the scanner can see is one that can be released.

### Added

- **Round-trip integration tests for the highest-traffic operations** (#133): of 218 `[ServiceAction]` methods, only 8 were genuinely executed against PowerPoint anywhere in the repository. `shape add-shape`, `shape set-fill`, `text set` and `chart create` all worked, and none had a test that would notice if they stopped.
  - `ShapeRoundTripTests` asserts the requested `MsoAutoShapeType` and bounds actually land on the shape, that `set-fill` writes the requested colour, and that a shape plus its text and fill survive save and reopen.
  - `TextRoundTripTests` asserts `text set` round-trips exactly, writes **only** to the named shape, and replaces rather than appends.
  - `ChartRoundTripTests` asserts `chart create` produces the requested `XlChartType` at the requested bounds.
  - `SlideMetadataTests` gains coverage of `slide read`, which populates layout and master names through a different code path from `slide list`, and asserts the two agree.
  - **Two tests assert against raw COM rather than our own read path.** A mutate-then-read-back test cannot detect a symmetric error: if `SetFill` and `ReadFill` both inverted PowerPoint's `0x00BBGGRR` byte order, the round trip would agree with itself and stay green while every shape rendered the wrong colour. The colours used are deliberately asymmetric (`#112233`) for the same reason.
  - Each assertion was verified to be load-bearing by inverting its expected value and confirming the test fails.

### Changed

- **The integration gate now re-runs only the suites a change can actually affect** (#143 follow-up): a full gate run is ~11 minutes and launches PowerPoint roughly 200 times, and it ran in full for every push — including pushes that touched only documentation or a single unrelated project. A gate that expensive on every push is a gate that ends up disabled.
  - Each suite's inputs are now derived from its **transitive `ProjectReference` closure**, not a hand-maintained list, so the mapping cannot silently drift from the build graph. The fingerprint is a SHA-256 over `git ls-files -s` for those paths, which uses git's own blob SHAs as the content hash rather than re-reading files.
  - A suite whose fingerprint matches the previous manifest is carried forward and marked `reused`, with the commit it was actually verified on recorded in `reusedFrom`. The pushed commit's evidence therefore still names the run that produced it.
  - Reuse is refused unless the previous manifest and the current run are both `binding=commit`. `git ls-files` reports the index, so on a dirty tree its blob SHAs would describe content that no commit holds — the same reason the gate refuses to mint evidence from a dirty tree at all.
  - Measured effect: a change confined to `src/PptMcp.Core` now reuses `cominterop-full`, skipping 96 tests and ~96 PowerPoint launches, while every suite that genuinely depends on Core still runs. A docs-only push reuses all six suites and completes in ~2 seconds with zero PowerPoint launches.
  - `-Force` re-runs everything, for when a result is suspected flaky or environment-dependent rather than stale. `-ListInputs` prints each suite's derived paths and fingerprint and exits without running anything, so the dependency mapping can be audited without paying for a run.

- **Scriban bumped 6.6.0 → 7.2.6**: resolves NU1904 (critical) and four NU1902 (moderate) NuGet audit advisories that broke `dotnet restore` and caused the scheduled CodeQL workflow to fail on `main` since July
- **StreamJsonRpc bumped 2.24.84 → 2.25.29**: clears the transitive `MessagePack` 2.5.198 (2 high, 9 moderate) and `Nerdbank.MessagePack` 1.0.2 (1 high, 2 moderate) advisories. `dotnet list package --vulnerable --include-transitive` is now empty
- **All 33 open npm advisories resolved** (17 high, 14 moderate, 2 low): transitive dependencies were refreshed in `vscode-extension`, `src/PptMcp.Agent` and `eval`, clearing advisories in `undici`, `form-data`, `tmp`, `lodash`, `js-yaml`, `brace-expansion`, `picomatch`, `fast-uri`, `linkify-it`, `markdown-it`, `qs`, `uuid`, `@azure/identity` and `@azure/msal-node`. Only lock files changed — no declared dependency version was altered, and all affected packages are build-time only, so nothing shipped in the extension package was affected. `npm audit` now reports 0 vulnerabilities in all three manifests

### Added

- **The integration suite is now an enforced gate instead of an honour system** (#143): `powerpoint-integration` in CI is unreachable twice over (no `ENABLE_POWERPOINT_INTEGRATION_CI` variable, no `powerpoint`-labelled runner, both confirmed at 0), and the self-hosted runner it needs has been **declined** rather than left pending. Nothing downstream of a developer's keyboard could run a test against real PowerPoint.
  - `scripts/Invoke-LocalIntegrationGate.ps1` runs the integration surface on the local machine — CLI smoke workflow, MCP smoke, the full ComInterop assembly, Core, CLI and MCP suites — mirroring the steps of the unreachable CI job so the two cannot drift in what they claim to cover. Including ComInterop only became affordable because #148 cut it from 33m to 7m.
  - It writes `.integration-evidence/manifest.json` (gitignored) **bound to a commit SHA**, recording each suite's test count, result and duration plus machine and PowerPoint version.
  - `scripts/check-integration-evidence.ps1` rejects every way the evidence could lie: missing, wrong schema, a different SHA, produced from a dirty tree (`binding=none`), a recorded failure, no suites, or any suite reporting zero tests. **Stale evidence is worse than none, because it looks like coverage.**
  - `scripts/pre-push.ps1` blocks any push touching `src/` or `tests/` without valid evidence for the pushed commit. Pre-push rather than pre-commit because the suite takes tens of minutes and per-commit enforcement would simply stop people committing. Override is `PPTMCP_SKIP_INTEGRATION_GATE=1`, which prints a banner naming the unverified commit so a skip is visible rather than habitual.
  - **`scripts/install-hooks.ps1` added, because the documented hook install never worked.** `Copy-Item scripts\pre-commit.ps1 .git\hooks\pre-commit` fails on every commit — git runs hooks through its own shell, which refuses a PowerShell file without a `.ps1` extension. Verified by reproducing it. The installer writes an `sh` shim per hook with LF endings and no BOM. No hooks were installed on this machine at all, so the pre-commit gates had never once fired automatically.
  - All five gate paths proven by probe: refuses without evidence, refuses evidence for another SHA, refuses `binding=none`, passes loudly under the override, and stays silent for docs-only pushes. The first probe found a real bug (a `-Verbose` parameter colliding with the PowerShell common parameter) that would have made the hook error out instead of judging anything.
  - `integration-runner-disabled` job text and `docs/AZURE_SELFHOSTED_RUNNER_SETUP.md` rewritten to state the decision as settled and point at the local gate, replacing language that implied a runner was merely pending.

### Fixed

- **Two concurrent callers could each open a PowerPoint session** (#132): `SessionManager.CreateSession` and `CreateSessionForNewFile` enforced the single-instance invariant with an unsynchronised check-then-act - `_activeSessions.IsEmpty` tested first, `TryAdd` called roughly 2.5 seconds of file I/O and COM bootstrap later. Each dictionary operation is atomic on its own; the sequence is not. `TryAdd` could not backstop it because the key is a freshly generated GUID and never collides.
  - **REPRODUCED:** two threads released from a barrier produced `succeeded: 2, failed: 0` on both create paths - two live sessions against a single-instance COM server, 100% of the time.
  - **FIX:** the single slot is now reserved atomically *before* the bootstrap begins, so the losing caller is rejected immediately instead of paying for a PowerPoint launch it is not allowed to keep. The reservation is released in a `finally`; on the success path the session is already published, so the slot never appears free in between.

- **CLI integration tests silently ran against the wrong service** (found by the new local gate, #143): three `DesignCommandTests` failed with `Archetype 'org-chart' not found` during a full gate run, yet passed when run in isolation.
  - **ROOT CAUSE:** `ServiceFixture` hosts a `PptMcpService` **in-process** on the CLI pipe name and configures it through in-process test hooks (the reference-catalog override). Windows permits multiple server instances per pipe name, so a `pptcli` daemon left running by an earlier suite answered the CLI's connection instead. That daemon has none of those hooks, so it loaded the real catalog. The failure was therefore ordering-dependent and invisible to any single-suite run.
  - **FIX (two independent nets):** `Invoke-GuardedTest.ps1` gained guard 5, which stops stray `pptcli` daemons before every run — unlike PowerPoint, a daemon is disposable state, never the developer's open document. `ServiceFixture` now pings the pipe before starting and refuses to run, with a message naming the culprit, if anything already answers.
- **The local gate could bind evidence to a commit it had not tested** (#143): the working tree was checked only at the start of the ~10-minute run, so anything edited under `src/` or `tests/` mid-run was still recorded against the starting SHA. The tree and HEAD are now re-checked at the end, and a run that moved underneath itself is downgraded to `binding=none`.

- **PowerPoint sessions took 8-48 seconds to tear down** (#148): the `PptMcp.ComInterop.Tests` assembly ran in **33m25s**; it now runs in **6m53s** (92 tests, all passing) and `Dispose()` dropped from 5.5s typical / 45s worst case to **1.1s**. Two independent root causes, both found by measurement rather than by the issue's stated hypothesis — which was falsified: `Quit()` never ran to its 30s timeout, succeeding in 151-680ms every time.
  - **ROOT CAUSE 1 — an abandoned COM proxy blocked the STA thread from exiting.** Session bootstrap called `((dynamic)tempPowerPoint).Presentations.Open(...)`, an inline chain that materialises a `Presentations` RCW bound to no local, so it could never be released. The STA thread then could not exit, `Join()` ran to the full 45s `StaThreadJoinTimeout`, and the thread was force-killed — exactly the 48-second single-assertion test cited in the issue. **FIX:** the collection is bound to a local and released in `finally`. A/B measured: leaky 45093ms vs clean 5501ms.
  - **This directly implicates #137.** The 173 baselined inline COM chains are not merely hygiene debt — one of them was the single largest cost in the test suite.
  - **ROOT CAUSE 2 — `Application.Quit()` and releasing the application proxy waited on each other.** Measured on a bare STA thread with no wrapper and no message filter: with `Quit()`, releasing the application blocked **40-60s**; without it, the release took **3-18ms**. PowerPoint refuses `Visible = false` ("Hiding the application window is not allowed"), and a visible instance does not exit when its last external reference drops, nor does it honour `WM_CLOSE`. **FIX:** `Quit()` was removed; the shutdown sequence now releases every reference cleanly (`FinalReleaseComObject` + GC) and then terminates the process, which is now the designed path rather than an emergency fallback.
  - The OLE message filter was **proven uninvolved**: instrumented across a 44.5s block it recorded `msgPending=0, incomingRejects=0, retryRejected=0`.
  - **Caveat, unchanged from previous behaviour:** because PowerPoint is single-instance, a session may attach to an instance the user already had open, and that process is terminated at session end. The prior code force-killed in the same situation, so this is not a regression; there is no reliable way to distinguish the two cases, and skipping termination leaks a process that locks files for every later session. Documented in `PptBatch.Dispose`.
  - Regression test `SessionShutdownCleanlinessTests` covers **both** bootstrap paths (open-existing and create-new) and asserts Dispose completes in under 10s, that no stuck-STA-thread error is logged, and that no PowerPoint process survives.
  - `ResiliencePipelines.CreatePowerPointQuitPipeline()` was removed as dead code, and `PowerPointQuitTimeout` renamed to `PowerPointShutdownTimeout` since nothing quits any more.

- **Nothing stopped new swallowed exceptions from being added** (#126): Rule 22 forbids catch blocks that suppress failures and Rule 1b requires Core commands to let exceptions reach `batch.Execute()`, but neither was enforced by anything. `scripts/check-swallowed-catches.ps1` now fails the build on any **new** catch in `src/PptMcp.Core/Commands` that neither rethrows nor performs loop control.
  - The existing population is frozen in `scripts/swallowed-catches-baseline.txt` (18 entries) and paid down under #126. The gate's job is to stop the count growing, which required no judgement call about code nobody has re-tested
  - **The issue's figure of 63 was wrong, and so was my own first measurement.** Scoped to `Core/Commands` there are 61 catch blocks in total: 40 optional-property probes, 18 swallows, 3 rethrows
  - **Rule 22 and Rule 1b genuinely conflict** on one shape of code - Rule 1b lists "optional property access" as a *safe* pattern while Rule 22 says never swallow. The gate takes a position instead of failing code the instructions bless: a **single-statement** `try` is a probe of a COM property that may not exist on this shape, and its absence is a value being unavailable rather than an operation failing. A `try` wrapping several statements is real work, and swallowing there hides a genuine failure. Rule 22 now documents this
  - Detection is brace-matched rather than regex-matched, and comments and string literals are blanked while preserving offsets. Without that the scanner reported the word "catch" inside an XML doc comment on `SlideCommands.GetSlides` as a violation - two false positives that would have made the gate untrustworthy on day one
  - Proven RED by injecting a multi-statement swallow, which was reported at its exact `file:line`, and GREEN again on revert
  - Wired into `pre-commit.ps1` and `hosted-checks.yml`; the CI static-gate list is now **12**

- **`ComInterop.Tests` does terminate as a full assembly; the "hang" was a wall-clock misdiagnosis** (#139): the issue recorded the assembly "running past 40 minutes with no completion" across repeated attempts, which left the project with no full-suite baseline at all. Re-run at current `main` under the guard, it **completes: 91 tests, 91 passed, 0 failed, in 33m25s** - the first completed full-assembly run this repository has measured.
  - The earlier 25-minute attempt was killed by the timebox, not deadlocked. `--blame-hang` wrote the sequence file the issue said was missing: 59 tests `Completed="True"` and one in flight, `SessionManagerOperationTrackingTests.IsPowerPointVisible_SessionWithShowPowerPointFalse_ReturnsFalse`. That test passes standalone in **48 s**, so it is not a hanging test - it was simply the one executing when the clock ran out
  - The cost is arithmetic, not pathology. `xunit.runner.json` correctly pins this assembly to `maxParallelThreads: 1` with collections serialized, so 91 tests that each create and quit a real PowerPoint run strictly one at a time. Roughly 20-48 s apiece is ~34 minutes, which is what was measured
  - `--blame-hang --blame-hang-timeout 300s` did not fire, confirming no test exceeded the threshold
  - The likely cause of the original observation is the orphaned-`testhost` defect fixed above: a previously killed run leaves a `testhost` still executing tests and spawning PowerPoint, which then competes with the new run for the single-instance COM server. Repeated attempts would each start from a dirtier machine than the last
  - Stale claims corrected: `Invoke-GuardedTest.ps1` and Rule 16 both asserted this suite "does not terminate". They now carry the measured figure and warn that `-Full` here needs `-TimeoutMinutes` above the 20-minute default, since 34 > 20 would otherwise cut every full run short
  - `OleMessageFilterTests`, previously red, passes in this run

- **A timed-out guarded test run kept launching PowerPoint forever** (#139): `Invoke-GuardedTest.ps1` guard 2 terminated the run with `Stop-Process -Id $proc.Id -Force`, which kills *only* the named process. `dotnet test` spawns a vstest console, which spawns `testhost` — and `testhost` is the process that actually executes tests and creates PowerPoint instances. Killing the parent orphaned `testhost`, which carried on running the suite, with nothing left watching it.
  - Observed directly, not theorised: after a 25-minute timeout reported "Cleaning up 1 PowerPoint process(es)", a POWERPNT started **27 seconds after the kill**, and killing it by PID produced another one. `testhost` (started before the kill) was still alive. Terminating that single orphan stopped the respawning immediately
  - This is the mechanism behind runaway PowerPoint after an aborted run: guard 3 swept the strays *once*, while the orphan kept making new ones
  - Guard 2 now kills the whole process tree, deepest descendant first so nothing re-parents and escapes; guard 3 sweeps repeatedly until the count converges, and prints an explicit `WARNING` with the surviving PIDs if it cannot
  - Proven by deliberately timing out a run at 1 minute: the guard reports `killed the process tree (3 descendant process(es), incl. testhost)`, and both `testhost` and POWERPNT stay at 0 through a settle period. Before the fix the same scenario left an orphan spawning PowerPoint
  - Added `-ExtraArgs` so diagnostics such as `--blame-hang` run *through* the guard, keeping the timebox and PowerPoint cleanup attached, instead of being a reason to call `dotnet test` directly

- **The COM leak gate could not fail** (#125): `check-com-leaks.ps1` backed Rule 5 ("must report 0 leaks") and the pre-commit table claimed it verified "all `dynamic` COM objects have `ComUtilities.Release()` in finally". It did neither. It asked two whole-file yes/no questions — does this file contain *any* `dynamic` acquisition, and does it contain the text `ComUtilities.Release` — and printed "Proper COM cleanup" whenever both were true. Every one of the 33 command files contains at least one `Release`, so every one was green, permanently.
  - Demonstrated rather than argued: injecting a blatant never-released `dynamic x = someObject.Application.ActivePresentation;` into `SlideCommands.cs` left the verdict unchanged — still "Proper COM cleanup", still "Leak files: 0", still exit 0. Rule 5 was satisfied vacuously rather than actually
  - Rewritten to track **each variable**: every `dynamic` that acquires a COM object must have a matching `ComUtilities.Release(ref <name>)` or `ReleaseIfNotNull`. The same injection is now caught with its exact file:line
  - **Ownership decides, not syntax.** A `dynamic` bound to `ctx.Presentation` is *borrowed* — the batch owns it, and releasing it would tear down the caller's presentation. There are 20 such aliases; flagging them would have produced 20 false positives, and a gate that cries wolf gets switched off. They are exempt by rule
  - Of 219 tracked acquisitions the new gate found **3 genuine Rule 22 leaks**, all fixed here rather than baselined, so the baseline ships **empty**:
    - `TransitionCommands.GetTransition` leaked the `SlideShowTransition` proxy on every call
    - `TransitionCommands.CopyToAll` leaked `srcTrans`, and leaked a further transition proxy **per slide** inside its loop
    - `ShapeCommands` group leaked the `Application` reference (10 other sites already release theirs, so the fix follows existing practice)
  - Proven RED before its GREEN was trusted, including re-running the exact injection the old gate had waved through. Documentation corrected: the gate checks that a release exists, not that it sits in a `finally`, and Rule 5 now says so plainly instead of overclaiming

- **381 of 580 tests were unreachable by any feature filter** (#138): Rule 16 tells contributors to run only the tests for what they changed, via `--filter "Feature=<name>"`. That instruction was unexecutable for two thirds of the suite. Ten classes carried no `Feature` trait, and six of those carried **no traits at all** — the issue reported only the missing `Feature` traits. Such a class can only be reached by the full 45-minute suite, which is to say: in practice it never ran.
  - Traits added to all ten: `ParameterValidation` (378 cases), `CoreCoverage` (66), `ResultTypes` (38), `ShapeHelpers` (37), `Design` (5), `PptContext`, `OleMessageFilter`, `ComUtilities`. Names were chosen to fit the vocabulary already in use rather than invented alongside it
  - Verified by discovery rather than assertion: `dotnet test --list-tests --filter "Feature=<name>"` now resolves each one, and every count matches the source exactly (`ShapeHelpers` = 1 `[Fact]` + 36 `[InlineData]` = 37; `ParameterValidation` = 126 + 252 = 378). `--list-tests` discovers without executing, so no PowerPoint was launched
  - New `scripts/check-test-traits.ps1` gate is the mirror image of `check-test-filters.ps1`: that one proves every documented filter resolves to a real trait, this one proves no test hides where no filter can reach it. It checks **per class, not per file** — and that distinction immediately found an eleventh class the per-file scan had missed, hidden behind a traited sibling in the same file
  - A trait counts as present on the class *or* on every test method, since both leave the tests reachable; failing a class that is genuinely selectable would be a false alarm, and false alarms are how gates get switched off. Proven RED four ways, including removing just **one** of eleven method-level traits. Only `Category` and `Feature` are required, because no filter in the repository selects on `Layer`

- **llm-tests gated on five tools that do not exist** (#136): the suite was inherited from an upstream Excel project and kept naming its tools — `range`, `range_format`, `table`, `chart_config`, `screenshot`. The issue listed four; `screenshot` was a fifth. The damage was not a broken test but a vacuous one: `allowed_tools=["chart", "table", "file", "range", "slide"]` restricted the model to a set where **three of five were fictional**, and `assert result.tool_was_called("table")` could never be true.
  - Remapped by reading what each test actually asks the model to do, not by pattern-matching names: `table`/`range`/`range_format` → `slidetable` (which owns `write-cell`, `format-cell`, `set-cell-border`), `chart_config` → `chart`, `screenshot` → `export` (which owns `slide-to-image`). Docstrings naming a nonexistent `set-style` action were corrected too
  - New `scripts/check-llm-test-tools.ps1` gate compares every tool named in `allowed_tools=[...]` and `tool_was_called("...")` against the **generated** tool surface — the same ground truth `check-documented-counts.ps1` uses, so it cannot drift from what the server exposes. Proven RED by reintroducing `table`, which it reported with exact file:line. Wired into `pre-commit.ps1` and the Hosted Checks workflow
  - The gate is scoped to those two call shapes rather than scanning for bare names, so ordinary Python survives — `for i in range(20)` in `cli/conftest.py` is not a tool reference. It also fails when it finds no references at all, so a refactor cannot silently retire it

- **Zero tests ran in CI, and the check list implied otherwise** (#143): the `powerpoint-integration` job is gated on a repository variable that is unset *and* targets a self-hosted runner that does not exist, so it is unreachable twice over. Everything merged on build and CodeQL alone, while a green `integration-runner-disabled` check made pull requests look verified.
  - New **Hosted Checks** workflow runs on `windows-latest` on every pull request: **37 COM-free tests** (skill generation quality, parameter transforms, service registry JSON parsing, and the action-enum completeness tests that guard Rule 15) plus **all 9 static gates**. Membership is by a hard rule — a test qualifies only if it never references `PptSession`, `BeginBatch` or `Presentation` — and every count is pinned with `-MinimumTests`, so a rename shrinks the job into a failure rather than into silence
  - The placeholder job now states plainly, in its log and in the PR job summary, that the integration suite **did not run** and that it executes no tests. It still reports success, because a required status check that never reports blocks every pull request — but it no longer reads as coverage
  - This does not replace the integration suite; ~580 COM tests still cannot run on a hosted runner. Choosing between a self-hosted runner and documenting integration tests as developer-machine-only remains open on #143

- **`Invoke-GuardedTest.ps1` refused the one suite it was meant to allow**: the COM-free allow-list matched on `Split-Path -Leaf`, which yields `Foo.Tests.csproj` when given a project file — the spelling every workflow uses — so it never matched and `SkillGeneration.Tests` was rejected as PowerPoint-driving. Now compared without the extension. Found by using the guard rather than by reading it

- **`Invoke-GuardedTest.ps1` could not stop a run from launching PowerPoint hundreds of times**: the wrapper failed on zero-match filters but was otherwise indifferent to how much work it started. An unfiltered `dotnet test` on any COM suite creates a PowerPoint instance per test — dozens to hundreds of consecutive launches, with no timeout and no cleanup. Rule 16 already forbade this in prose, and prose did not hold.
  - **Unfiltered runs of PowerPoint-driving projects are now refused**, exiting 1 before `dotnet` is invoked at all. A whole-assembly run is still possible, but requires the explicit `-Full` opt-in that CI now passes
  - **Every run is timeboxed** (`-TimeoutMinutes`, default 20) and killed on expiry. Without this, a wedged suite keeps spawning PowerPoint for as long as nobody is watching
  - **PowerPoint processes leaked by the run are cleaned up**, matched by PID against a snapshot taken before the run starts, so a developer's own open presentation is never killed
  - The project allow-list is inverted deliberately: a project is assumed to drive PowerPoint unless named as safe, so a newly added COM suite is guarded on the day it lands rather than the day someone remembers to list it

- **Required status checks could never pass on documentation- or dependency-only pull requests**: `build-cli` and `integration-runner-disabled` are required checks on `main`, but both workflows were restricted to source paths. A skipped check never reports a status, so any pull request that did not touch those paths stayed permanently blocked with "the base branch policy prohibits the merge".
  - ROOT CAUSE: a required status check combined with a `paths` filter — GitHub treats "skipped" and "never reported" identically for branch protection
  - FIX: removed the `paths` filter from the `pull_request` trigger of `build-cli.yml`, `integration-tests.yml` and `codeql.yml` so the required checks always report. The `push` filters are unchanged, so pushes to `main` still skip irrelevant builds
- **Dependency review license gate rejected the GitHub Copilot CLI**: `@github/copilot` and its nine platform-specific packages ship under their own `LICENSE.md` rather than an SPDX identifier, so the license checker classified them as incompatible and failed every pull request that touched those lock files. They are now exempt from the license check only — vulnerability scanning still applies to them.
- **`master` tool threw `RuntimeBinderException` on every action**: `list`, `list-shapes`, `edit-shape-text` and `list-layouts` all read `Presentation.SlideMasters`, which does not exist in the PowerPoint COM API.
  - ROOT CAUSE: property carried over from a spreadsheet-oriented code base; PowerPoint exposes masters through `Presentation.Designs.Item(i).SlideMaster` (one master per design)
  - FIX: added a shared `GetMaster(presentation, masterIndex)` helper that resolves masters through `Designs`, and routed all four actions through it
- **Layout lookup failed on non-English Office installations**: `slide create --layout Blank` and `slide apply-layout` raised "layout not found" because `CustomLayout.Name` and `CustomLayout.MatchingName` are both localized (for example `Leer`, `Titelfolie`, `Zwei Inhalte` on a German install).
  - ROOT CAUSE: lookup compared only against the localized `Name`, and the COM API exposes no locale-independent layout identifier
  - FIX: `FindLayout` now resolves in stages — exact `Name`, then `MatchingName`, then position within the first design using the canonical Office layout order (which is identical across locales). Canonical English names and numeric indices both work; the not-found message now lists the layouts that are actually available
- **Release workflow would have published a version below the current release**: the next release was calculated as `v0.1.0` even though `v1.0.3` is already published.
  - ROOT CAUSE: `git describe --tags` only finds tags that are ancestors of `HEAD`. No release tag is an ancestor of `main` in this repository, so the command failed and the `|| echo "v0.0.0"` fallback silently swallowed the error
  - FIX: the workflow now selects the highest semver tag with `git tag -l --sort=-v:refname`, which is independent of ancestry, and fails loudly if the tag cannot be parsed instead of emitting a bogus version
- **MCP resources advertised tools that do not exist**: `ppt://help/resources` and `ppt://help/quickref` told LLMs to call `powerquery`, `datamodel`, `namedrange`, `connection` and `range`, none of which are registered by this server, and documented `presentationPath`/`sessionId` parameters instead of the actual `path`/`session_id`.
  - ROOT CAUSE: the resource provider was carried over unchanged from the spreadsheet-oriented code base and never validated against the generated tool surface
  - FIX: both resources now describe the real tools (`slide`, `shape`, `text`, `notes`, `slidetable`, `comment`, `section`, `design`, `vba`, `export`, `file`) with the parameter names the generated tools actually expose
- **Agent skill CLI reference was never regenerated and shipped spreadsheet commands**: `skills/ppt-cli/references/cli-commands.md` listed `pivottable`, `slicer`, `powerquery` and `worksheetstyle`, and contained no parameters or actions at all.
  - ROOT CAUSE: three independent defects in `scripts/Build-AgentSkills.ps1` — it looked for `pptcli.exe` under a hardcoded, wrong target framework and silently skipped generation; it parsed the English section headers `COMMANDS:`/`OPTIONS:`, which Spectre.Console localizes, yielding zero commands on a non-English host; and it expected an `Actions:` prefix that the command descriptions do not contain
  - FIX: the target framework is now read from the csproj, section headers are matched locale-independently, actions are taken from the generated `ServiceRegistry` files, and every failure mode now throws instead of emitting an empty or stale reference
